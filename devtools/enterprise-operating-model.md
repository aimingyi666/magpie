## 1. 项目目标和范围冻结

### 1.1 最终目标

企业版必须同时满足四个结果：

1. **员工能用：** 企业 OIDC 登录后，本地 Magpie 在 5 分钟内完成设备和 Agent 配置；员工
   只能访问授权模型和企业 MCP，失败时有明确恢复路径。
2. **管理员能管：** 用户、组织、设备、凭证、额度、模型、MCP、资源、策略、用量和告警都
   在权限和组织范围内管理，敏感操作可追溯。
3. **安全能证明：** 身份、权限、审计、脱敏、留存、吊销、备份、恢复和回滚都有可重复证据，
   不依赖页面隐藏或口头承诺。
4. **上游能同步：** 企业代码隔离，上游变更每小时可被检测；冲突在功能分支解决，企业发布
   可独立灰度、回滚和停止。

### 1.2 范围冻结规则

每个交付包进入开发前必须冻结以下内容：

- 目标员工范围、部门范围、试点人数和退出条件。
- 必须交付的功能 ID、接口、数据迁移和权限。
- 不在本包内的能力，以及临时替代流程。
- 验收证据、责任人、上线签字人和回滚负责人。
- 依赖的 IdP、SCIM、MDM、网络、模型、MCP、Secret Manager 和监控系统。

任何新增范围必须回答：

```text
为什么现在必须做
对应哪个需求 ID 和交付包
是否会修改上游跟踪文件
是否新增身份、权限、数据、秘密或外部依赖
对工期、容量、成本、验收和回滚的影响
谁批准范围和预算变更
```

不能在当前交付包未验收时，用“顺手加一个页面”或“先接一个 MCP”绕过阶段门禁。

### 1.3 明确不做的事

- 不把 Magpie 改成多租户 SaaS，不重写模型路由核心。
- 不把浏览器当成员工电脑的任意文件配置器；本机 Agent 只能由本地 Magpie/helper 修改。
- 不默认采集对话正文；L2/L3 必须经过合规批准、独立权限和访问审计。
- 不把页面隐藏按钮当作权限控制；所有权限在服务端校验。
- 不在 50-100 人试点前引入多地域、Kubernetes 或复杂微服务。
- 不直接读写 `caller-keys.json` 完成调额或模型授权。
- 不以 Mock、演示或“接口返回 200”代替真实网关、真实 IdP 和真实终端验收。

## 2. 角色、职责和 RACI

### 2.1 必需角色

| 角色 | 核心职责 | 不能兼任的职责 |
| --- | --- | --- |
| 项目发起人 | 预算、跨部门协调、最终上线授权 | 不能单独批准自身权限提升 |
| 产品负责人 | 范围、员工体验、优先级和验收标准 | 不能单独批准高风险正文访问 |
| 架构/技术负责人 | 服务边界、上游兼容、ADR、安全设计评审 | 不能独自发布未经复核的核心改动 |
| 平台/后端研发 | auth、admin、gateway-control、数据模型、接口和测试 | 不能直接修改生产数据替代正式迁移 |
| 前端/客户端研发 | 员工门户、管理台、本地加入和配置流程 | 不能绕过服务端权限 |
| IT/身份团队 | IdP、SCIM、DNS、代理、MDM、终端和网络出口 | 不能未经批准扩大管理员范围 |
| SRE/运维 | 部署、监控、备份、容量、灰度、回滚和值班 | 默认不能查看业务正文 |
| 安全/隐私 | 威胁模型、密钥、漏洞、告警、阻断和事件响应 | 不能单方面修改审计留存证据 |
| 合规/审计 | 正文权限、留存、法律保留、导出和审计证据 | 不负责业务配置变更 |
| 试点部门负责人 | 员工组织、培训、反馈、使用纪律和退出协调 | 不能查看其他部门数据 |

同一人可以承担多个小型项目角色，但以下职责必须分离：

- 申请高权限的人不能是唯一审批人。
- 执行生产发布的人不能是唯一验收签字人。
- 查看正文、删除审计证据和修改留存策略不能由同一人静默完成。
- 修改密钥的人不能同时是唯一审计复核人。

### 2.3 决策和升级

| 决策类型 | 默认决策人 | 必须会签 | 升级条件 |
| --- | --- | --- | --- |
| 功能范围和优先级 | 产品负责人 | 架构、试点部门 | 影响预算或上线日期 |
| 核心代码 hook、数据模型和 API | 架构负责人 | 平台、SRE、安全 | 影响上游兼容或迁移 |
| IdP、SCIM、MDM 和网络出口 | IT/身份负责人 | 安全、产品 | 影响全公司登录或办公网 |
| 正文审计、导出和留存 | 合规负责人 | 安全、审计、产品 | 涉及员工隐私或法律保留 |

紧急权限只能用于阻断正在发生的风险。使用后必须在 24 小时内补充原因、范围、证据和复核；
不能把 break-glass 变成日常路径。

## 3. 设计、评审和变更控制

### 3.1 何时必须写 ADR

以下变更必须先有 ADR 或等效设计记录：

- 修改上游跟踪文件、核心 Provider、路由、网关鉴权、`gwmw` 中间件或客户端配置行为。
- 新增身份事实来源、权限模型、组织范围、跨部门查询或正文访问能力。
- 新增外部服务、数据库、消息队列、Secret Manager、KMS、mTLS 或多副本。
- 新增 API 契约、数据迁移、持久化格式、幂等或审计状态机。
- 改变 Key 签发、刷新、轮换、吊销、额度或模型白名单的真实生效方式。
- 改变发布、更新源、MDM、回滚、备份或生产值班流程。

ADR 至少记录背景、备选方案、选择、风险、回滚、兼容性、权限/秘密影响和验证方式。ADR 与
代码、测试、文档和回滚说明放在同一个 PR 中。

### 3.2 评审门禁

| 评审 | 触发条件 | 必须产出 |
| --- | --- | --- |
| 架构评审 | 新服务、核心 hook、数据模型或外部依赖 | 边界图、失败模式、回滚方案 |
| 安全评审 | 身份、权限、秘密、正文、网络出口或管理员能力 | 威胁模型、滥用场景、负向测试 |
| 隐私/合规评审 | 正文、工具参数、导出、留存或跨境 | 数据分类、告知、权限和保留期限 |
| SRE 评审 | 生产部署、容量、备份、HA 或发布 | 容量假设、健康检查、恢复演练 |
| 上游兼容评审 | 修改 `internal/`、`cmd/`、GUI 或构建链 | 最小 hook、默认关闭、回归计划 |

评审不通过时，可以在隔离原型中继续验证，但不能合并到 `main`，不能进入试点或生产环境。

## 4. 团队协作节奏

以下是建议默认节奏，可按团队规模调整；调整后必须保持证据和责任不丢失。

| 节奏 | 参与人 | 输出 |
| --- | --- | --- |
| 每日 15 分钟 | 研发、SRE、安全值班 | 阻塞、依赖、当日验收目标 |
| 每周一次交付评审 | 产品、架构、研发、SRE | 本周完成、下周计划、风险和新 ADR |
| 每周一次安全/隐私评审 | 安全、合规、架构 | 高风险变更、正文权限、事件和例外 |
| 每两周一次试点复盘 | 产品、IT、试点部门 | 使用率、失败原因、培训缺口和退出条件 |
| 每月一次项目委员会 | 发起人、产品、架构、SRE、安全 | 预算、范围、里程碑和 go/no-go |
| 每次发布前 | 产品、SRE、安全、架构 | 发布证据包、回滚点、值班和通知 |
| 每季度一次演练 | SRE、安全、IT、审计 | 备份恢复、吊销、越权、事件和上游同步演练 |

每个功能分支必须指定：

```text
负责人
对应工作包/需求 ID
目标阶段和交付包
依赖项
验收命令或证据路径
回滚点
```

PR 审查 SLA 建议：

- P0 安全/生产阻断：工作时间内 2 小时响应。
- P1 当前里程碑：1 个工作日内给出实质意见。
- P2 非阻断改进：3 个工作日内处理。

超时未处理的 P0/P1 必须升级到架构负责人，不允许通过放宽测试或跳过评审“赶进度”。

## 5. GitHub 协作和分支治理

### 5.1 分支模型

| 分支/标签 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 同步上游和合入已验收企业 PR | 禁止直接开发、直接提交和人工直接推送 |
| `feat/<模块>-<描述>` | 新功能 | 从最新 `origin/main` 创建，一个 PR 只做一个切片 |
| `fix/<模块>-<描述>` | 非紧急缺陷 | 从最新 `origin/main` 创建，附复现测试 |
| `security/<编号>-<描述>` | 安全问题 | 限制可见范围，修复和证据同步评审 |
| `sync/upstream-<日期>` | 上游冲突处理 | 只解决同步冲突，不夹带业务功能 |
| `release/ent-YYYY.MM.DD-N` | 发布准备 | 只接受已验证提交、版本号和证据修正 |
| `ent-vYYYY.MM.DD-N` | 不可变发布标签 | 禁止移动或覆盖 |

当前企业阶段的已实现基线和主分支顺序：

```text
C4-01 gateway-key JSON contract（已完成本地测试）
  -> C4-02 gateway-control adapter（已完成 Mock/故障测试）
  -> feat/m2-c4-gateway-policy
  -> feat/m2-c5-operations-audit
```

不得接触真实员工凭证。C4-03c 的本地 Mock/故障链路不等于生产验收。每个分支必须从最新
`origin/main` 创建，PR 前合入 `upstream/main`；
不得把这些切片堆在一个分支或一个大 PR 中。

### 5.2 功能分支生命周期

1. 在 Issue 或工作包中冻结目标、验收和不在范围内的事项。
2. 从最新 `origin/main` 创建功能分支；禁止从另一个未验收功能分支搭车。
3. 开发过程中每天或至少每次提交 PR 前合入 `upstream/main`。
4. 在功能分支解决冲突，不在 `main` 上解决。
5. 提交代码、测试、文档、迁移、回滚说明和实际测试结果。
6. 提 PR，等待 CODEOWNERS、CI、安全和上游兼容检查。
7. 使用合并提交合入 `main`，保留功能边界；禁止 force push `main`。
8. 合并后运行关键回归；失败时回退合并提交或停止发布，不覆盖企业历史。

### 5.3 `main` 分支保护

GitHub 仓库应配置规则集或分支保护，最低要求：

- 禁止直接 push 和 force push，禁止删除 `main`。
- 要求 PR 才能合并；至少 1 名非作者审批，高风险改动要求 2 名。
- 新提交自动撤销旧审批，未解决评论不能合并。
- 启用 CODEOWNERS；核心、安全、数据和发布目录必须有对应 owner。
- 要求 CI 检查通过，包括语法、单测、企业服务测试、构建、秘密扫描和文档链接检查。
- 要求分支与 `main` 最新状态一致，防止未合并的上游变更被忽略。
- 默认禁止 bypass；仅经安全负责人批准的真人紧急维护可按 break-glass 流程使用管理员
  bypass，并保留安全记录和 24 小时内的事后复核。
- 上游同步工作流使用专用 GitHub App 或受控机器人，只授予创建分支和 PR 所需的
  `contents: write`、`pull-requests: write`；不得授予受保护 `main` 的 bypass 或 force push。
- 同步失败必须产生可见告警；不能让机器人强制覆盖、reset 或跳过冲突。

当前 `sync-upstream.yml` 每小时合并并直接推送 `main`，这只是历史实现，不得作为企业默认。
企业目标态必须改为“创建同步分支 -> 合并 `upstream/main` -> 运行 CI -> 自动创建 PR ->
必需检查通过后合入受保护 `main`”。机器人和同步工作流永远不能直推受保护 `main`，也不能
通过 bypass 绕过必需检查；冲突、测试失败或需要人工判断时停在同步分支并告警。人工紧急
bypass 仅限上述 break-glass，且必须保全证据并接受事后复核。

### 5.4 必须的 CI 门禁

| 门禁 | 内容 | 阻断条件 |
| --- | --- | --- |
| 语法/格式 | Go、Node、Shell、PowerShell、Markdown | 格式或解析失败 |
| 单元测试 | Go、admin-service、auth-service | 任一测试失败 |
| 集成测试 | 隔离 Magpie、Mock OIDC、mock 上游 | 请求归属、刷新、撤销失败 |
| 权限测试 | RBAC、组织范围、CSRF、跨部门读写 | 越权或依赖调用未阻断 |
| 审计测试 | intent/result、幂等、审计失败阻断 | 伪造成功或秘密进入审计 |
| 秘密扫描 | 仓库、日志、响应、构建产物 | 发现 Token、Key 或 Secret |
| 构建 | CLI、服务镜像、安装包 | 不可重现或产物缺失 |
| 文档检查 | 相对链接、需求 ID、状态口径 | 链接失效或把设计写成已实现 |

CI 失败不能通过删除测试、放宽断言或改变状态字段“让它变绿”。属于已知上游问题的失败必须有
Issue、临时豁免期限和负责人。

### 5.5 PR 模板

每个 PR 固定包含：

```text
## 目的
## 对应需求/工作包
## 影响范围和兼容性
## 是否修改上游跟踪文件
## API、数据迁移和配置变更
## 权限、组织范围、审计和秘密处理
## 失败、重试、幂等、回滚和灰度
## 实际运行的测试命令与结果
## 未验证项和禁止宣称的结论
## 回滚点
```

审查者必须确认：

- 代码行为与文档一致，没有把 `pending`、`partial_success` 或 `unknown` 显示为已生效。
- 服务端执行认证、权限、组织范围和目标校验，不只依赖前端隐藏。
- 响应、日志、审计和测试产物不含 Key、token hash、设备令牌或服务令牌。
- 新增依赖、许可证和外部网络出口已经记录。
- 失败路径有测试，不把依赖超时或审计失败当作成功。

### 5.6 上游同步策略

正常运行：

```text
每小时 fetch upstream/main
  -> 干净合并
  -> 推送 main
  -> 触发企业关键回归
  -> 全部通过后保留同步点
```

冲突时：

```text
保留 main 最后一个已验证同步点
  -> 创建 sync/upstream-<日期>
  -> 在同步分支解决冲突
  -> 运行全量回归和安全检查
  -> PR 合入 main
  -> 更新企业发布点
```

禁止：

- 为“保持实时”强制覆盖企业提交。
- 在 `main` 上手工解决大冲突。
- 让同步失败阻塞紧急安全修复；安全修复走独立分支和独立发布点。
- 把上游最新提交直接部署到员工，不经过企业构建、灰度和验收。

固定信任边界：

```text
admin-service
  -> auth-service（用户级 gatewayPolicy、版本、operation）

  -> magpie gateway-key describe/policy apply（固定 argv，无 shell）
  -> 专用 XDG_CONFIG_HOME + caller-keys.json
  -> 独立 describe 回读和真实请求行为验证
```

- admin-service 只能只读挂载 `usage.jsonl`，禁止直接读写 `caller-keys.json`，也禁止获得
  网关配置目录写权限。
- `gateway-control` 只允许 describe、policy apply 和健康检查；用户可控值只能是已校验的
  Key ID、稳定模型 ID、整数额度和枚举周期，不能变成任意命令、路径或 shell 参数。
- `gateway-control` 使用专用低权限服务账号，只挂载必要的配置子目录；不读取 issuer Key、
  OIDC Secret、设备令牌、管理员 Cookie 或管理员会话数据，不访问 Docker socket。
- `gateway-control` 不映射宿主机或公网端口，只加入内部服务网络；当前与 auth-service 之间
  使用独立、可轮换的 Bearer 服务令牌，不是 mTLS，不能复用 `AUTH_ADMIN_TOKEN`、
  `AUTH_INTERNAL_ADMIN_TOKEN`、`MAGPIE_ISSUER_KEY` 或管理员 Cookie。生产应升级到
  mTLS/SPIFFE/工作负载身份。
- 默认超时 10 秒、单次输出上限 64 KiB；超时必须终止子进程。日志只记录动作、Key ID、
  策略版本、耗时和稳定错误码，不记录完整 CLI 输出、token、账户 ID 或 Secret。
- `policy apply` 成功不等于生效。写入后必须再独立执行一次 `describe`，比较模型、额度窗口
  和 `policyRevision`；只有回读一致且真实请求行为符合策略时才标记 `known`，否则保持
  `pending` 并进入对账。

禁止事项：

- 解析人类可读的 `gateway-key limit/models` 文本作为生产回读依据。
- 用多次 `limit add/off`、`models all` 等命令拼接目标状态，制造可见中间状态。
- 在管理页把 `pending`、`partial_success`、`failed` 或 `unknown` 显示为“已生效”。
- 在 `expectedVersion` 或 `expectedPolicyRevision` 冲突时覆盖其他管理员的变更。
- 自动回滚或静默重试依赖；重试和回滚必须由 C5 生成可审计的子 operation。

详细字段、状态机、接口和验收证据见
[`enterprise-feature-spec.md`](enterprise-feature-spec.md) 第 12.8.1.5 节、
[`enterprise-master-plan.md`](enterprise-master-plan.md) 的 M2-C4 工作包，以及
[`enterprise-deployment.md`](enterprise-deployment.md) 第 10 节。

## 6. 环境、晋级和数据隔离

| 环境 | 用途 | 数据 | 允许人员 | 晋级条件 |
| --- | --- | --- | --- | --- |
| 本地开发 | 单元测试、Mock、脚本验证 | 临时目录、假数据 | 研发 | 单测和静态检查通过 |

- 生产数据不能复制到开发环境；需要排查时使用脱敏导出和受控临时目录。
- 任何环境晋级都必须关联 commit、PR、测试证据、迁移、回滚点和负责人。

## 7. 发布、灰度和证据包

### 7.1 发布对象

企业发布至少包含：

- 企业 Magpie CLI/客户端和安装包。
- auth-service、admin-service、gateway-control 和模型/MCP 网关镜像。
- 组织、角色、额度、模型、MCP 和资源策略。
- 数据迁移、配置模板、密钥引用和更新源清单。
- 部署、备份、恢复、回滚和值班手册。

### 7.2 发布流程

1. 从已验证的 `release/ent-*` 或不可变 tag 构建，不从开发分支直接发布。
2. 在预生产运行全量回归、真实 IdP、权限、审计、备份恢复和容量检查。
3. 生成发布证据包，确认所有未验证项和禁止宣称的结论。
4. 先在 5-10 人或单部门灰度，观察登录、签发、调用、错误、额度和审计。
5. 检查真实 `usage.jsonl`、网关回读、管理操作和对账状态。
6. 达到观察窗口且没有 P0/P1 问题后扩大范围。
7. 保留上一镜像、上一客户端、上一策略和数据库备份作为回滚点。

### 7.3 发布证据包

```text
release tag / commit / image digest
upstream merge point
PR 和工作包列表
变更说明、影响范围和不在范围内的事项
数据库/配置/密钥迁移说明
语法、单测、集成、E2E、权限和审计结果
真实 IdP、代理、Docker、Windows、真实网关和用量卷验证
秘密扫描、SBOM、签名、漏洞扫描和制品哈希
备份点、灰度范围、观察指标和告警阈值
回滚步骤、回滚负责人和回滚验证
培训、通知、客服和值班安排
未验证项、已知风险和批准人
```

证据包缺少关键项时，版本只能进入演示或受控试点，不能进入生产候选。

### 7.4 灰度、回滚和停止条件

出现以下任一情况立即停止扩大范围：

- 员工无法登录、设备无法注册、短期 Key 无法刷新或请求归属错误。
- 员工可绕过企业网关访问未授权模型/MCP，或跨部门读写成功。
- 敏感操作没有 intent/result 审计，或依赖失败被显示为成功。
- 管理台显示“已生效”但真实网关请求仍可越权或额度未生效。
- 响应、日志、审计或前端产物出现 Key、token 或 Secret。
- 备份恢复、吊销、回滚或上游同步关键回归失败。

回滚优先顺序：

1. 停止新流量和新签发，保留现有审计证据。
2. 回退客户端更新源或资源 manifest。
3. 回退网关/控制面镜像和配置。
4. 回退数据迁移或从备份恢复，必须有逆向脚本和验证记录。
5. 对已执行但未确认的操作走 C5 子 operation 和人工对账，禁止静默重放。

## 8. 依赖、假设和许可

### 8.1 外部依赖

| 依赖 | 必需能力 | 未满足时的处理 |
| --- | --- | --- |
| 企业 IdP | OIDC Authorization Code + PKCE、MFA/ACR、JWKS、稳定 `sub`、停用事件 | 只做隔离演示，不接真实员工 |

| Secret Manager/KMS | Key、OIDC Secret、Session、服务令牌和 issuer Key | 不得使用明文 `.env` 上生产 |
| MDM | 签名安装、更新源、版本锁定、卸载和回滚 | 手工安装只限受控试点 |
| 网络出口 | 员工机只能访问企业网关和允许的 MCP | 未锁出口时不能宣称防绕过 |
| 模型供应商 | 稳定模型 ID、价格版本、额度和数据条款 | 未确认时不能发布部门预算 |
| MCP/Skill 来源 | 版本、哈希、许可证和安全负责人 | 未确认时不得分发 |
| SIEM/OTel | 元数据导出、告警和检索 | 没有可观测性时不能进入生产运营 |
| PostgreSQL/Redis | M6 的共享存储、限流和 HA | 50-100 人前不强制，之后按容量决策 |

### 8.2 许可和合同检查

- Magpie 是 MIT 许可，企业内部使用和再分发必须保留版权声明。
- 模型、MCP、插件、字体、图标、容器基础镜像和扫描工具分别检查许可证。
- 模型供应商的数据使用、保留、跨境、训练、滥用监控和企业条款必须经法务/安全确认。
- 审计正文采集必须完成员工告知、隐私影响评估、留存/删除规则和访问审批。
- 第三方插件不得默认进入企业白名单；需要版本锁定、来源验证和退出方案。

## 9. 容量、成本和技术预算

### 9.1 容量驱动

容量评估至少收集：

```text
日活员工数、峰值并发、每小时请求数
每请求平均/峰值输入输出 Token
模型 P95 延迟、流式比例、重试率
设备心跳和刷新频率
usage.jsonl 日增量、审计事件日增量和留存天数
管理查询并发、导出大小和报表频率
告警、日志、Trace 和备份副本数
灰度期间同时运行的版本数
```

规划公式：

```text
网关峰值 QPS = 日活 × 活跃小时请求数 ÷ 3600 × 峰值系数
原始用量存储 = 日请求数 × 平均事件字节 × 留存天数 × 副本数
正文审计存储 = 日请求数 × 采集比例 × 平均正文字节 × 留存天数 × 副本数
备份空间 = 原始数据 × 备份份数 × 保留代数
```

峰值系数、事件大小和采集比例必须用真实试点数据校准，不能只用厂商上限估算。

### 9.2 规模分层

| 规模 | 建议架构 | 重点 |
| --- | --- | --- |
| 5-50 人 | 单网关 + auth/admin + Compose，单机备份 | 身份、短期 Key、权限、审计和退出通道 |
| 50-200 人 | 网关与控制面分离，反向代理，只读报表，定期恢复演练 | 额度/模型授权真实生效、看板、SCIM |
| 200-500 人 | PostgreSQL、Redis 限流、监控/SIEM、灰度发布 | 容量、HA、审计留存和运营值班 |
| 500+ 人或强合规 | 多副本、KMS/mTLS、多地域、ClickHouse/对象存储 | RPO/RTO、供应链、数据驻留和压测 |

### 9.3 成本分类

预算至少分为：

- 模型调用和 Token 成本。
- 网关、控制面、数据库、对象存储、备份和出口流量。
- 审计、SIEM、日志、监控和长期留存。
- 身份、MDM、KMS、证书、WAF 和公司基础设施分摊。
- 研发、SRE、值班、培训、客服和安全评审人力。
- 第三方扫描、渗透测试、许可证和合规评估。

成本控制手段：

- 按人、部门、Agent、模型和 Key 设额度与告警。
- 默认路由选择经批准的低成本模型，禁止未经批准的自动扩大回退。
- 对长上下文、附件、缓存和大报表设置上限。
- 正文审计按风险和部门分层采集，不做全量默认采集。
- 每月复核未使用模型、异常 Key、失控设备和重复资源。

本文件不承诺具体金额；金额必须在真实 IdP、模型价格、人数、留存和基础设施报价完成后由
财务/采购确认。

## 10. 培训、客服和变更管理

### 10.1 培训对象

| 对象 | 培训内容 | 最短验证 |
| --- | --- | --- |
| 员工 | 登录、设备注册、一键配置、错误恢复、隐私边界 | 5 分钟内完成一次真实调用 |
| 部门管理员 | 组织范围、用户/设备、额度、模型、MCP、资源和审计查询 | 完成一次无越权操作 |
| 安全管理员 | 告警、阻断、吊销、事件和证据保全 | 完成一次设备丢失演练 |
| 审计员 | 元数据查询、正文授权、导出、留存和法律保留 | 完成一次受控查询和访问审计 |
| SRE | 部署、健康检查、备份、恢复、灰度和回滚 | 完成一次隔离恢复 |
| 客服/IT 支持 | 常见错误、日志收集、升级路径和禁止操作 | 能正确分流 P0-P3 |

### 10.2 员工沟通

上线前必须提供：

- 企业 AI 使用范围、不得输入的数据和模型出口说明。
- 审计等级、正文是否采集、留存期限和访问审批。
- 设备丢失、离职、密钥失效、网络中断和模型不可用的处理方式。
- 客服入口、故障公告和隐私/安全问题上报渠道。

禁止用“完全匿名”或“绝对不记录”描述存在元数据审计的系统。

### 10.3 支持分级

| 级别 | 示例 | 首次响应 | 目标恢复 |
| --- | --- | --- | --- |
| P0 | 全公司无法登录、Key 泄露、越权或数据外泄 | 15 分钟 | 1 小时内阻断，4 小时内恢复 |
| P1 | 单部门大面积不可用、额度/模型错误 | 30 分钟 | 4 小时内恢复或降级 |
| P2 | 单员工加入失败、资源同步延迟 | 1 个工作日 | 2 个工作日内解决 |
| P3 | 文档、界面、体验和优化建议 | 3 个工作日 | 进入迭代计划 |

客服不能要求员工发送 Gateway Key、OIDC Token、Cookie、设备令牌或完整请求正文。排障使用
`requestId`、`operationId`、时间、模型 ID、错误码和脱敏日志。

## 11. 试点、退出和生产上线

### 11.1 试点进入条件

- M0/M1/M2-A/M2-B 在真实内网、真实 IdP 和受控员工机完成验收。
- 至少一个部门有明确负责人、使用名单、培训计划和退出通道。
- 备份、吊销、回滚、客服和值班责任明确。
- 员工机、网关和控制面均无厂商 Key、长期员工 Key 或服务令牌泄露。
- C4-03c、C4-03d、C5 和 M2-D 的核心能力虽已实现，试点范围仍不包含尚未完成生产环境
  验收的自助管理能力。
  C4-04 已通过隔离真实 Magpie E2E，但不代表 Docker/共享卷、真实企业 IdP、反向代理和生产
  网关已经验收；C4-03a 只提供管理端只读目录，不代表真实员工模型授权已在生产生效。

### 11.2 试点运行

建议 4-6 周，先 5-10 人，再扩到单部门 50 人以内。每周记录：

- 首日/首次成功率、5 分钟可用率、刷新失败和重启恢复。
- 请求成功率、P95 延迟、模型/网关错误、额度误判和用量归属。
- 跨部门拒绝、CSRF、会话过期、设备丢失和离职吊销演练。
- 工单分类、培训缺口、员工反馈和绕过尝试。
- 上游同步次数、冲突、回归失败和发布回滚。

### 11.3 试点退出条件

满足以下条件才能进入生产候选：

- 连续 2 周无 P0，P1 有根因和修复证据。
- 员工 5 分钟可用率达到约定门槛，失败可自助恢复或有明确客服路径。
- 离职/设备丢失在目标时间内阻断新刷新和心跳，当前 Key 按撤销周期失效。
- 跨部门读写全部被服务端拒绝，依赖调用为 0。
- 敏感操作有 intent/result、理由、目标、操作者和 `operationId`。
- 真实 `usage.jsonl` 可归属、可轮转、损坏可检测，管理容器不能写网关卷。
- 备份恢复、上游冲突、客户端回滚和至少一次故障注入通过。
- 安全/合规/审计确认数据出口、告知、留存和正文权限。

任一项未满足，试点继续或回退，不得用“员工先用起来”替代门禁。

### 11.4 生产上线决策

上线会议必须逐项确认：

```text
范围、人数、部门和生效时间
真实 IdP、代理、Docker、Windows、MDM 和网络证据
C4/C5/D、M3-M5 中本次实际启用的功能
权限、组织范围、审计、正文和导出边界
容量、成本、值班、客服和回滚点
未验证项、已知风险和批准人
停止推广和全量回滚的触发条件
```

产品、架构、IT、SRE、安全和审计负责人分别签字。缺少任一签字，只能保持试点或生产候选。

## 12. 事故、安全和持续运营

### 12.1 安全事件流程

1. **发现：** SIEM、告警、员工报告或审计发现异常。
2. **分级：** 确认是否涉及 Key、越权、正文、模型外泄或大范围不可用。
3. **阻断：** 停用用户、吊销设备、撤销 Key、限制 IP、关闭模型/MCP 路由或暂停资源发布。
4. **保全：** 保存原始审计、`operationId`、网关回读、日志哈希和操作记录。
5. **恢复：** 轮换秘密、修复缺陷、验证未授权访问已停止，再逐步恢复。
6. **复盘：** 根因、影响面、时间线、责任、修复、回归和客户/员工通知。

紧急吊销必须优先于“保持会话可用”。任何恢复操作都要生成新的审计记录，不能修改历史证据。

### 12.2 日常运营清单

| 周期 | 任务 |
| --- | --- |
| 每日 | 查看登录/签发/刷新/网关错误、异常用量、同步失败和安全告警 |
| 每周 | 审查失败工单、额度异常、设备漂移、上游同步和未处理高风险操作 |
| 每月 | 权限和角色复核、未使用 Key、用量/成本、备份抽检和发布复盘 |
| 每季度 | 备份恢复、设备丢失、离职、跨部门越权、Key 泄露和上游冲突演练 |
| 每半年 | 访问策略、许可证、供应商条款、容量和 DR 目标复核 |
| 每年 | 渗透测试、供应链审计、隐私影响评估和生产签字续期 |

### 12.3 关键运营指标

- 员工首次可用时间 P95、登录/刷新/心跳成功率。
- 请求成功率和 P95 延迟、模型/网关错误率。
- 撤销生效时间、未归属请求数、额度拒绝率和成本偏差。
- 跨部门拒绝率、依赖调用为 0 的越权次数。
- 敏感操作审计完整率、`pending`/`partial_success` 对账时长。
- 资源同步 P95、漂移设备数、回滚成功率和上游同步延迟。
- 备份恢复成功率、RPO/RTO、P0/P1 响应和恢复时间。

指标必须来自真实服务、日志和审计，不从页面手工填数。

## 14. 最终完成定义

企业版项目只有以下条件同时成立才算完成：

1. **组织就绪：** 每个工作包有负责人、验收人、预算、时间窗口和回滚负责人。
2. **工程就绪：** 分支保护、PR、CI、秘密扫描、上游同步、迁移和回滚全部可重复。
3. **员工就绪：** 真实 IdP 登录、设备注册、短期凭证、本地一键配置和授权模型/MCP 可用。
4. **管理员就绪：** RBAC、组织范围、敏感写操作、真实网关生效、操作查询和失败对账可用。
5. **安全合规就绪：** L0 审计完整，L2/L3 有独立权限和审批，告警、吊销、留存和导出可证明。
6. **运维就绪：** 监控、容量、备份、恢复、灰度、回滚、值班和生产签字全部有证据。
7. **上游就绪：** 每次上游合并后关键回归通过，企业发布可以独立于上游节奏前进或停止。

以上任一项缺失，当前版本只能停留在对应交付包，不得对外宣称“企业生产版已完成”。
